## 2026-11-03（夜）変化検知を前倒しで実装

- **変化検知は Haiku 5.5 を tool use で呼ぶ**。ツールは `get_baseline` / `get_recent_logs`（14日）/ `get_weather`（スタブ：日誌の天候列を返す）。最終出力も `report_detection` ツール（strict）で受け、`level` / `reasons` / `next_checks` / 説明2種 / `confidence` を DATA_MODEL §3 の形で得る。`tool_choice` は auto（強制しない）。理由：Haiku 5.5 は強制するとツール呼び出し前に考えないため、先に基準値と履歴を読ませたい
- **浴槽温度の判定ルール（湯守の指示）**：冬季の目標 43℃。±1℃以内は平常、±2℃超は要確認（check）。1〜2℃の間は経過観察（watch）と解釈した。**冬季は 12〜2月**と定義（模擬データの季節補正と同じ）。冬季以外の目標は未決定なので、その季節は浴槽温度だけで check にしない。小野さんに決めてもらう
- **「湯量増加＋チャンバー温度低下の同時発生」を check のルールに加えた**（eval S10「混入の可能性」より）。湯量が基準の +5% 超かつチャンバーが基準の −5% 以上低下、を暫定の目安にした。eval で磨く
- **出力の言い回しをコードでも検査する**：「効く／治る／安全／保証」等を含む出力は差し戻して書き直させ、直らなければ保存しない。check/watch では「要確認」「管理者の確認を」を必須にし、2回直らなければ末尾に定型文を足す。プロンプトだけに頼らない（CLAUDE.md 絶対ルール3）
- **説明文は当面 Haiku が同じ呼び出しで書く**（DATA_MODEL §3 の出力に含まれるため）。PRD の「説明文は Sonnet」は引き継ぎメモ(D4)とあわせて 11/5 に再検討
- **API 利用の上限**：開発中のテストは 5 件まで（PRD §8）。`npm run eval` は全件を回す設計だが、今日の実測は 5 件に絞って行う（`--only`）。残りは小野さんが `npm run eval` で回す
- **detection に `confidence` 列を追加**（DATA_MODEL §3 の出力に含まれるため）
- **11/3 湯守の判断基準4件を eval と検知に組み込み。現場由来と想定を origin で区別**。基準は `data/yumori_rules.json`（R1 浴槽40℃割れで引湯管に付着→湯量低下／R2 約3か月ごとの引湯管清掃／R3 浴槽38℃割れは危険信号／R4 冬は湯量全開・来客前に保温シート）。`origin: field` は湯守の実体験・判断基準、`hypothetical` はそこから派生した想定。検知プロンプトには「この施設の湯守が定めた判断基準」として渡し、field を優先して理由に `湯守の判断基準（R1）` の形で引用させる。画面・README・動画でも field と hypothetical を混同させない（CLAUDE.md「推測と確認済み事実を区別」）
